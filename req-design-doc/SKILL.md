# 需求设计与实现规划

## 目标与原则
输出可交付编码 Agent 的 Markdown 规格书；不猜测高风险决策、不虚构现有代码事实、不未经授权启动执行工具。默认只生成设计文档，不修改业务代码。

## 工作流程

### 1. 判断场景和分析现状
- 区分新项目、已有项目迭代、仅生成 PRD、仅补充设计。
- 若有仓库访问权限，先只读检查 README、目录、依赖、入口、接口、数据模型、测试和构建命令；优先复用现有架构。没有权限则说明限制，不声称已扫描。
- 区分用户明确要求、仓库中已验证事实、合理假设和待确认问题；不得将假设写成事实。

### 2. 分级澄清需求
按影响分级，不要为了低风险细节反复打断：
- P0 必须确认：权限、隐私/数据删除、外部付费、不可逆操作、核心业务语义、与现有系统冲突的关键决策。
- P1 建议确认：技术选型、接口契约、性能目标；提出默认方案及影响，用户允许按假设继续时可推进。
- P2 可默认：文件命名、普通日志格式、非关键 UI 文案；写入假设记录。
- 用户明确要求仅出草案时，即使 P0 未确认，也可以输出标记为「待确认、不可直接实施」的草案，不能假装规格已确定。
- 同类问题合并提问；不要对用户已明确回答的内容重复确认。

### 3. 编写规格
使用 [references/template.md](references/template.md)，按任务规模删减不相关章节。必须包含：
1. 目标、范围内/范围外、现状依据与假设。
2. 具体功能及逐项可验证的验收标准。
3. 技术栈及版本：已有项目沿用可验证的现状；无法确认的版本标记待核实，不编造。
4. 文件变更清单、模块职责、关键数据流。
5. 有接口时定义方法、路径、请求响应、错误码、鉴权；有持久化时定义字段、类型、约束、迁移及回滚。
6. 边界与异常、权限与安全、性能及兼容性要求（适用时）。
7. 按依赖顺序排列的实现任务，每项列出验收方法、测试命令（已知时）和失败处理。
8. 决策记录：已确认事项、假设、未决问题与风险。

### 4. 质量检查与交付
- 检查每条需求能映射到任务和验收标准；检查接口与数据模型前后一致。
- 检查测试命令是否存在于当前环境；未运行的测试标记「未执行」，绝不声称通过。
- 保存到用户指定路径；无文件写入能力则在对话中提供完整 Markdown，不虚构保存路径。
- 交付文档、未决事项及下一步执行建议。

### 5. 可选编码执行
- **只有用户明确授权开始编码时**，才调用当前环境实际提供的编码 Agent 或工具。
- 不绑定 Claude Code、Codex、OpenCode 或某一专用命令；按可用工具能力选择。若工具不可用，交付手工执行指引。
- 执行前确认目标仓库、分支和范围；推送、部署、删除数据等高影响操作需单独确认。
- 任务完成后汇报实际变更、测试结果、剩余风险；不得将设计文档视为已实现的功能。

## 输出标准
简洁、可执行、可追溯；小需求使用精简模板，复杂系统使用完整模板。优先减少无效确认，不牺牲关键安全与正确性。
